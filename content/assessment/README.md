# Practice checks, calibration, and transfer

Each lesson now has three short applied checks in addition to its original quiz and three exercises. They ask you to predict a failure, interpret a trace, and apply the concept in another situation. The prompts and pass criteria live in [learning metadata](../learning.json) and appear in the portal exercise workspace. They have no embedded answer key.

Attempt a check before reopening the lesson. Write an explanation, not just a verdict. Compare it against the stated criteria and identify the observation that supports your conclusion. If you need a hint, record the help level. A remembered answer and an independently reproduced artifact are different evidence.

Use [calibration specimens](calibration.md) to see what weak, adequate, and strong work looks like in other domains. The annotations assess specific dimensions, not imaginary whole-course scores.

At each stage gate, attempt the corresponding [transfer task](transfer-and-retention.md) without copying your Signal Desk answer. Use the same concept with new inputs. Add errors or uncertain explanations to your recall queue; revisit them after a delay and adjust the interval based on what you can explain.

## Record a useful review

A useful review contains four statements:

1. **Criterion:** the precise requirement being assessed.
2. **Evidence:** the sentence, artifact, command output, or trace that bears on it.
3. **Gap:** the unsupported claim, missing case, or remaining uncertainty.
4. **Next action:** one small revision or experiment that would resolve the gap.

Use the [attempt record](../../templates/exercise-attempt.md) for offline work. Preserve attempt 1 when adding attempt 2. Mark feedback as self-review, tutor, peer, or reproduced execution. A tutor may suggest a test; only actually running it produces execution evidence.

## Practical mastery stays explicit

Quiz completion checks one recognition task. Applied checks test explanation and transfer. Reviewed exercises test larger artifacts. Execution gates test the actual implementation and named environment. None automatically substitutes for the others.

Use the [assessment manual](../../docs/ASSESSMENT.md) for stage gates and capstone minimums. If a dependency or live model is unavailable, mark that integration pending and continue the route you can execute. Do not turn an unavailable requirement into a silently awarded pass.
