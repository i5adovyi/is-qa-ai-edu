# 24 · How to build a small project with your assistant, then grow it

## Start here

A **capstone** is a project that combines things you have learned. It does not mean you must now build an autonomous production platform alone. Begin with one useful behavior you can understand and check, then add complexity only when it teaches something important.

For an SDET, a good first project is an assistant that proposes test cases from a short requirement and clearly distinguishes suggestions from executed tests. You can explore that behavior in a conversation before creating files. The original full capstone briefs remain available as later targets; this guide is the bridge to them.

## The idea in plain language

A **prototype** is a small implementation or demonstration used to explore an idea. A **vertical slice** is one complete but narrow user journey: provide one requirement, obtain one useful result, and check that result. It is more informative than several unfinished components that do not work together.

An **acceptance criterion** states what must be true for that slice to count as useful. For test suggestions, you might require that every expected result comes from the supplied requirement, unknown rules stay unknown, and the assistant never claims a proposed test has run.

Keep three levels of evidence distinct. A conversation can demonstrate the model's proposed behavior. A local program can demonstrate that its actual code handles specific inputs. An integrated model-and-tool run can demonstrate behavior across that particular integration. None automatically proves the others.

Growing the project means choosing the next missing behavior, such as loading a saved requirement, rejecting an unsupported test claim, or preserving an unfinished review. It does not mean adding retrieval, MCP, skills, multiple agents, and a database merely because those topics exist in the course.

The assistant may implement code for you. Your learning task is to understand what it changed, inspect the actual result, and make a small prediction before a rerun. Independent implementation can come later. If the assistant produces a program you cannot explain, ask for a smaller slice rather than accepting a larger mystery.

## A small example

Use this fictional requirement, unrelated to the retained QA capstone's seeded defect:

```text
R-NAME: A display name may contain at most 12 characters.
The product has not specified whether an empty name is allowed.
```

A useful suggested check uses a name with exactly 12 characters, such as `abcdefghijkl`, and expects it to meet the stated length rule. Another uses 13 characters, `abcdefghijklm`, and expects rejection for length. An empty name has an unspecified outcome; the assistant should identify the missing rule rather than choose one silently.

These are proposed checks, not test execution. We have not supplied an application to run. That small distinction already combines task scope, context, evaluation, and truthful reporting.

## Try it with Codex or Claude Code

1. Open either assistant. Paste the prompt below; it works without a clone or API key beyond the access you already use for that assistant.

```text
Help me begin a small QA assistant project, one step at a time.
Synthetic requirement R-NAME: a display name may contain at most 12 characters.
Whether an empty name is allowed has not been specified.
For this first step, do not create files, run tests, connect services, or solve
the academy's capstone. Propose three checks using lengths 12, 13, and 0.
For each, show its input, supported expected result or missing rule, and
status "proposed, not executed". Explain how I can verify your reasoning.
Then stop and ask me which result I want explained before any implementation.
```

2. Count the two non-empty inputs and inspect the empty-input uncertainty. Ask for a plain-language explanation of anything surprising.
3. If you choose to build, open the project using [the assistant quickstart](../../docs/ASSISTANT-QUICKSTART.md). Ask: “Create a new disposable prototype under `work/qa-first-slice/`, without changing academy source or existing student assignments. If that folder already exists, choose a fresh name and preserve its contents. Explain the files and commands before running them. Implement only the agreed length behavior and keep unspecified behavior explicit.”
4. Let the assistant inspect the available local runtime and show the actual command. If it cannot execute, keep the result labeled unexecuted; do not substitute a predicted green test report.
5. Inspect one real result, ask what would make it fail, and choose one further change. A useful next change is usually another requirement or evidence check, not an entire architecture.

## What you should see

The first result should contain proposed checks with supported expectations and an explicit missing rule. No output should say that an application passed when none was provided. A later local slice should come with actual files, a reproducible command, and real output identifying what ran.

You can progress in four manageable steps: understand one conversation result; run one local slice; add a small evaluation set; then select one retained capstone brief. The full brief may require broader evidence, failure drills, and a review package. The first slice is preparation, not a claim that those requirements are complete.

## If it goes wrong

If the assistant builds everything at once, stop and return to one behavior. If it silently decides the empty-name rule, ask where that rule came from. If tests pass because they merely repeat the implementation, compare them with the original requirement and try a deliberate boundary change. If setup fails, preserve the exact error and ask for one repair step. Do not spend the entire learning session installing optional infrastructure that this slice does not need.
