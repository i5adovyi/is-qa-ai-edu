# 23 · How to investigate a failure without guessing the cause

## Start here

An **incident** is a failure that disrupts expected operation enough to need attention. Here we use a small fictional failure; no real system, customer, or on-call process is involved. You need only the idea of a request passing through several steps.

An SDET can add particular value here: preserve evidence, separate the observed symptom from its possible cause, and turn a repaired defect into a regression test. AI may help interpret logs, but a confident explanation without supporting events remains a hypothesis.

## The idea in plain language

A **symptom** is what you observe: “No test summary appeared.” A **hypothesis** is a possible explanation: “The model may be unavailable.” A **trace** is a record of events for one run. Its timestamps, step names, outcomes, and identifiers help you locate where progress stopped.

**Triage** means assessing what is affected and deciding the immediate next action. **Containment** limits further disruption. **Recovery** restores useful operation and checks what happened to unfinished work. Finding a deeper cause and preventing recurrence may take longer than restoring the service.

A **runbook** is a set of practical operating instructions. It should name what to inspect and what a result means, rather than saying “check the AI.” A **postmortem** is a review after an incident: what happened, what evidence supports the account, what contributed, and what changes will reduce recurrence. Its purpose is learning and improved behavior, not blaming the last person who touched a setting.

Missing events create uncertainty. If a log lacks an event, it may mean the step never started, or it may mean logging failed. Seek another observation before treating absence as proof. Preserve the original evidence before rerunning something that could overwrite it.

Not every typo in a personal experiment needs a formal incident process. The useful habit scales down: observe, explain what is known, make one bounded change, and verify the result. In a real organization, communication and escalation follow its authorized procedures.

## A small example

This is an invented test-report import, separate from the academy's incident assignments:

```text
09:12:00 run DEMO-6: received report sample.csv
09:12:01 import: expected columns case,status
09:12:01 import: observed one column named case;status
09:12:01 import: stopped; summary step not started
09:12:02 operator note: "Probably the language model is down."
```

The observed boundary is the import step. The semicolon in the observed header suggests that the export may use a different column separator from the importer. That is a testable explanation. The operator note offers no evidence about model availability, and this trace says summary generation did not start.

A useful next inspection is the file's actual header and the importer's expected separator in a disposable copy. We have not inspected that file here. The trace does not justify announcing the complete root cause or silently editing real reports.

## Try it with Codex or Claude Code

1. Open either assistant. You can paste the entire example without a repository. The [assistant quickstart](../../docs/ASSISTANT-QUICKSTART.md) covers working with files later.
2. Paste this prompt:

```text
Teach me incident reasoning from this synthetic trace. Do not run commands,
open real files, solve academy incidents, or claim a repair has happened.
09:12:00 DEMO-6 received report sample.csv
09:12:01 import expected columns case,status
09:12:01 import observed one column named case;status
09:12:01 import stopped; summary step not started
09:12:02 operator note: Probably the language model is down.
Separate observations, hypotheses, and unknowns. Propose one next inspection
and one way to preserve the original evidence. Explain how a recovery check
would differ from simply retrying. Keep the answer under 250 words.
```

3. Check that observations are tied to actual trace lines. A proposed cause should stay labeled as a hypothesis until inspected.
4. Ask: “What evidence would contradict your current explanation?” This helps prevent the assistant from forcing every new observation into its first story.
5. Stop when you can distinguish a diagnosis from a verified repair. No incident report is required for the reading route.

## What you should see

The assistant should identify the import failure and the separator hypothesis, while leaving actual file content and importer configuration unverified. It should preserve the operator note as a claim, not adopt it as a fact. A recovery check should examine successful import, a truthful downstream result, and the status of the interrupted request.

If it claims to have opened `sample.csv`, it has invented execution: the name exists only in the supplied teaching trace. That distinction is central to trustworthy operational assistance.

## If it goes wrong

If it blames the model immediately, ask for the first failing recorded step. If it invents missing events, ask it to separate direct observations from inferences. If it recommends repeated retries, ask whether the input changed and whether a retry could overwrite evidence. If it jumps to a complete system rewrite, ask for the smallest inspection that can confirm or reject the current hypothesis.
