# 03 · Tell whether a prompt change actually helped

## Start here

You have a prompt that produces a useful-looking answer. Now you want to improve it. This lesson explains how to compare two versions without mistaking a nicer response for a more correct one. Read [clear requests](02.md) first if “expected output” is unfamiliar. You need no statistics software, API, or testing framework for the demonstration.

## The idea in plain language

An **evaluation**, often shortened to **eval**, is a planned check of an AI system's behavior. For an SDET, this is close to familiar test thinking: choose cases, define what should happen, observe what happens, and investigate mismatches. The difference is that model wording and sometimes decisions can vary across runs.

A **rubric** is a short set of scoring rules. For example, “The answer preserves the error code” is clearer than “The answer is good.” A **paired comparison** tests prompt A and prompt B on the same inputs, so different input difficulty does not explain the result. A **regression** is a case that worked before a change and fails afterward.

Change one main thing at a time. If you change the prompt, model, input examples, and scoring rules together, a better result cannot tell you which change helped. Keep an untouched group of cases for checking the final candidate. These are **held-out cases**: examples you did not repeatedly use to tune your prompt. Cases you inspect and tune against belong to development, even if you originally called them a final test.

You do not need a large benchmark for every personal request. For a one-off explanation, careful review may be enough. Repeated workflows, shared prompts, and decisions with consequences deserve a more deliberate comparison. Start small to discover failures, then broaden evidence before making claims about reliability.

## A small example

Imagine two prompts that summarize CI failures. CI means the automated build and test process that runs after code changes. We use invented candidate outputs here, not measured model results.

```text
Input: Test checkout_total failed. Expected 12.00, received 10.00.
No tax configuration was supplied.
Candidate A: Tax calculation is broken; fix the tax rules.
Candidate B: checkout_total expected 12.00 and received 10.00.
Tax configuration is unavailable, so the cause is unconfirmed.
```

Use two checks: preserve the observed mismatch, and avoid asserting an unverified cause. B passes both for this example. A asserts a cause the input does not establish. That supports a judgment about these two written answers only. It does not establish how often either prompt would pass across future tests.

Suppose a second case shows B dropping an important error code. Calling B “the winner” without recording that regression would hide a useful failure. Comparing cases individually tells you more than immediately collapsing everything into one percentage.

## Try it with Codex or Claude Code

1. Open a conversation in either assistant; the [quickstart](../../docs/ASSISTANT-QUICKSTART.md) covers setup if needed.
2. Paste the prompt below. It asks for a worked review of supplied outputs, so the assistant need not run a model experiment or access your CI system.
3. Read the justification for each check. Confirm it points to words that really appear in the input or candidate.

```text
Teach me a small evaluation using these synthetic candidates.
Input: checkout_total failed; expected 12.00, received 10.00;
tax configuration unavailable.
A: Tax calculation is broken; fix the tax rules.
B: checkout_total expected 12.00 and received 10.00; the cause is unconfirmed.
Checks: preserve the observed mismatch; avoid asserting an unverified cause.
Score each candidate against each check and explain using the supplied text.
Label this as review of authored examples, not a live prompt experiment.
Then explain what additional evidence would be needed to compare prompts.
Do not create files, run commands, or generate answers to academy exercises.
```

For a later actual comparison, use separate fresh conversations with the same synthetic input and record each raw response before scoring it. Say which assistant and visible model setting you used. The second conversation should not contain the first candidate's answer or your feedback about it. Even then, two observations remain a small sample.

## What you should see

The review should evaluate evidence support, not politeness or length. It should label the demonstration honestly. If you later collect actual responses, keep failures unchanged; correcting them before recording would erase the thing you need to learn from.

Your stopping point is understanding why “this answer passed two checks” is a narrower claim than “this prompt is reliable.” You can continue to [selecting context](04.md) without building an evaluation system today.

## If it goes wrong

If the assistant declares a percentage improvement from this single example, ask it to state the observed counts and limits instead. If it scores its favorite style rather than your checks, repeat the two rules. If both outputs look equally correct, use a case that tests a real uncertainty; adding arbitrary difficulty just to force a winner is unhelpful.

An AI judge can also make mistakes. Compare its explanation with the source yourself. Later evaluation lessons explore graders and repeated measurements; you need not solve those topics before learning this basic discipline.
