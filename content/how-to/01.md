# 01 · Understand what your AI assistant is doing

## Start here

Start with a familiar testing task: understanding a failed check. You only need to read this page. If you already use Codex or Claude Code, you can paste the example into its conversation and discuss it. There is no diagram to draw, repository to clone, or script to build before learning the idea.

An SDET is a software engineer who helps establish software quality through testing and automation. Your existing habit of asking “What evidence supports that?” is valuable here. The new part is learning which AI outputs are suggestions and which are observations of something that actually happened.

## The idea in plain language

A **language model** produces a response using the information supplied to it and patterns learned during training. It can explain an error, suggest test cases, or draft code. A fluent explanation can still be wrong. It does not become a test result because it sounds confident.

The **assistant** is the application you interact with, such as Codex or Claude Code. The model is one component inside it. Depending on its setup and permissions, the assistant may also read files or run commands. Those capabilities are **tools**: operations performed by software outside the model. Asking for a test command and actually running that command are separate events.

A **workflow** follows a sequence chosen in advance: read a failure, suggest a cause, then request a human review. An **agent** can choose some next actions from what it observes, such as deciding which file to inspect after a failed test. A **harness** is the surrounding software that gives that process its context, permitted tools, checks, records, and stopping conditions. You do not need to build one to begin using an assistant. These names help you understand later lessons and judge claims about automation.

Choose the smallest useful task first. If a failure says a required file is missing, reading the error may solve the problem. An autonomous investigation would add overhead. AI becomes more useful when you need help interpreting unfamiliar code, comparing plausible explanations, or finding missing cases. Your first success criterion can be modest: a clearer explanation with an honest statement of what is still unknown.

## A small example

Consider this invented test observation:

```text
Test: a new account should have zero saved filters.
Observed: expected 0, received 2.
Setup note: the account was copied from a shared test fixture.
No application code or database output has been supplied.
```

The observation establishes a mismatch between the expected and observed count. The shared fixture makes leftover data a plausible explanation. It does not prove that explanation. A useful assistant might say, “Check whether the copied fixture already contains filters.” A response saying “I cleared the database and fixed it” would invent both an action and its outcome.

Notice the division of work. The test runner produced an observation. The model can help interpret it. A person or authorized tool would inspect the fixture. A repeated test would provide new evidence. You can follow those responsibilities in ordinary sentences; no drawing is necessary.

## Try it with Codex or Claude Code

1. Open a conversation in the assistant you already have. If this is unfamiliar, use the [assistant quickstart](../../docs/ASSISTANT-QUICKSTART.md).
2. Paste the complete prompt below into its message box. The example is self-contained; it does not refer to files on your computer.
3. Read the response once. Then ask it to explain any unfamiliar word using the same example.

```text
Teach me how to use an AI assistant for SDET work. Use only this synthetic
example: a new account should have zero saved filters; the test received 2;
the account came from a shared test fixture. No code or database output
is available.
Explain the observed fact, one possible explanation, and one useful next
check. Label the explanation as unconfirmed. Explain which part is model
reasoning and which would require an actual tool result. Keep it short.
Do not edit files, run commands, or solve an academy assignment.
```

This is a worked demonstration, so an explanation is welcome immediately. If you subsequently choose an exercise, tell the assistant to wait for your attempt before giving its answer. You can also read the example here without sending the prompt anywhere.

## What you should see

Look for three distinct things: the count mismatch, a tentative explanation, and a check that could confirm or reject it. The assistant should not claim to have inspected a file or fixed the test. Wording will vary between responses; matching a particular sentence is unnecessary.

You have reached the stopping point when you can recognize “suggested,” “observed,” and “executed” as different claims. Proceed to [making a clear request](02.md) whenever ready. Reading this page does not mark an exercise complete.

## If it goes wrong

If the assistant starts coding, say: “Pause implementation. I only want the three-part explanation from the supplied facts.” If it invents a fixture name, ask which supplied line supports that name. If it gives six new technical terms, ask for one term at a time. These are ordinary course corrections, not evidence that you need an advanced setup.
