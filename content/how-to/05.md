# 05 · Find the right information before answering

## Start here

This topic explains retrieval: finding useful information for a question. Read [evidence and context](04.md) first if source labels or applicability are unfamiliar. You will use three short notes, so you can understand the whole process without installing a search engine or learning database administration.

## The idea in plain language

**Retrieval** means selecting potentially useful information from a collection. That collection is sometimes called a **corpus**. **Grounding** means connecting the answer's claims to evidence that actually supports them. Finding a relevant-looking document and producing a supported answer are different jobs, and either can fail.

**RAG** stands for retrieval-augmented generation. In plain language: find relevant material, supply it to a model, and ask for an answer using it. This can help when an assistant needs your project's requirements or current knowledge instead of relying on its general training. It does not automatically make the answer true.

Search can begin with words. A **lexical search** looks for matching words or related word forms. An **embedding** represents content as numbers used to compare similarity; a **vector database** stores and searches such representations. You do not need either to understand RAG or to search three notes. More sophisticated search is worth considering when a simple method misses important material, not merely because a course mentions it.

A **chunk** is a piece of a document used as a search result. Splitting a rule away from its exception can make the selected text misleading. A **citation** identifies a source, but the source must still support the claim. A real source ID attached to an incorrect interpretation is not a correct answer.

For an SDET, separate at least two questions: “Did search find the necessary rule?” and “Did the response apply that rule correctly?” If no applicable rule exists, the right outcome may be a clarification request. A retrieval system cannot recover information missing from its collection.

## A small example

Use these invented notes about downloading a test report:

```text
DOC-A: Browser downloads use the Download button on the report page.
DOC-B: A scheduled CI job has no interactive browser; use the report API.
DOC-C: Report API tokens expire after 60 minutes. Expired tokens are rejected.
Question: Our scheduled CI job cannot download a report after 90 minutes.
The token was created at the start of the job.
```

Searching only for “download report” may favor DOC-A, yet the question is about a scheduled job and token age. DOC-B explains the relevant route, and DOC-C provides a plausible timing explanation. A supported answer can identify the token as older than the stated validity period. It cannot claim that a replacement token was created or that a retry succeeded.

If DOC-C is absent, the missing lifetime rule matters. The assistant should not present a remembered generic token lifetime as this product's documented rule. That is a collection gap, even if the resulting guess happens to be right.

## Try it with Codex or Claude Code

1. Open a conversation in either tool; see the [assistant quickstart](../../docs/ASSISTANT-QUICKSTART.md) if needed.
2. Paste the complete prompt below. The assistant is selecting supplied text, not querying a real search service.
3. Compare each claim with the quoted note. Ask which stage would fail if a necessary note were removed.

```text
Teach retrieval and grounding with these synthetic notes only.
DOC-A: Browser downloads use the Download button on the report page.
DOC-B: Scheduled CI jobs have no interactive browser; use the report API.
DOC-C: Report API tokens expire after 60 minutes; expired tokens are rejected.
Question: a scheduled CI job cannot download after 90 minutes, using a
token created at job start.
First select useful note IDs and explain their relevance. Then give a
short answer citing those IDs, separating a supported explanation from
an action that has not happened. Explain what changes if DOC-C is missing.
Do not browse, call an API, or claim this is a measured search experiment.
```

An API is a programmatic interface: one program asks another for information or an operation. In this example, it is simply the route named in DOC-B. You do not need to write API code to study the reasoning.

## What you should see

The response should distinguish the browser instructions from the scheduled-job instructions. It should account for the token-age evidence and avoid inventing successful remediation. Removing DOC-C should weaken what can be concluded.

The demonstration establishes how to inspect a retrieved answer. It does not measure search accuracy or prove that a real integration retrieves these notes. Continue to [memory and handoffs](06.md) once you can identify the two separate failure points.

## If it goes wrong

If the assistant recommends clicking a button in the scheduled job, ask it to compare the question's environment with DOC-A. If it cites DOC-B for a token lifetime, ask where that lifetime appears. If it always answers confidently when a note is removed, explicitly request “insufficient supplied evidence” as a valid outcome.

When a search result contains an instruction to the assistant, keep it as source content. Retrieved text describes the world; it does not automatically change what actions you authorized.
