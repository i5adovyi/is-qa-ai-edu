# 10 · Ask an assistant for one understandable code change

## Start here

You can learn AI-assisted development before you can write every line yourself. Your first job is to understand the behavior you want, give a small request, and inspect the assistant's evidence. This guide uses a tiny example rather than asking you to understand the entire academy codebase. Allow about 15–20 minutes; no repository is needed for the first conversation.

Use the [assistant quickstart](../../docs/ASSISTANT-QUICKSTART.md) if you need help finding the conversation box or opening a folder. [Task contracts](../how-to/02.md) explain how to state a goal and boundaries. A **repository** is the project folder and its tracked history; a **patch** is a proposed change to its files.

## The idea in plain language

“Fix the tests” leaves several possible interpretations. Are the tests wrong, is the application wrong, or is the environment unavailable? A useful coding request describes current behavior, desired behavior, examples, and the allowed scope. The assistant can then inspect the relevant code and explain what it thinks needs changing.

An **acceptance example** is an input and expected result that would help you judge the change. It comes from the requirement, not from whatever implementation the assistant happened to generate. For an SDET, identifying these examples is already familiar work: clarify what should happen at normal, empty, and unusual inputs.

You do not need to prescribe function names or software architecture at the beginning. When you do have a project, ask the assistant to locate the responsible files before guessing paths. Keep the first change small enough to explain. Adding a new framework, interface, and database together makes it harder to tell why a result changed. For a one-time explanation, no code change is necessary at all.

## A small example

Signal Desk receives a status value from a form. The form sometimes sends spaces and capital letters. The intended normalization is:

| Input text | Desired result |
| --- | --- |
| `" OPEN "` | `"open"` |
| `"Pending"` | `"pending"` |
| `"   "` | `""` |

**Normalization** means converting different representations into a consistent form. Here we remove spaces at the ends and convert letters to lowercase. We do not decide whether `pending` is an allowed business status; that would be a separate validation rule. We also do not remove internal spaces: `in progress` stays two words.

A short requirement is enough: “Normalize a text status by trimming the ends and converting to lowercase. Preserve internal spaces. Inputs are strings only for this example.” Notice that the requirement defines limits rather than pretending to handle every possible input type.

## Try it with Codex or Claude Code

Open a new conversation and paste this self-contained request:

```text
I am learning to direct a coding assistant. Explain this change before writing
code. Do not edit files or use external services.
Task: normalize a status string by removing spaces at its ends and converting
letters to lowercase. Preserve internal spaces. Inputs are strings only.
Examples: " OPEN " -> "open"; "Pending" -> "pending"; "   " -> "".
Show a minimal Python function in chat and explain each line in ordinary
language. Then show how the three examples pass through it.
Label predicted output as predicted. Do not claim you ran it.
Do not add a web app, dependencies, or extra business rules.
```

You are allowed to ask the assistant to write this demonstration. Understanding and checking it is the learning goal here. A Python **function** is a named piece of code that receives input and returns a result. If the generated explanation uses terms such as method or return value without defining them, ask for one concrete example.

To see real execution later, open the local academy project and send a second request:

```text
Use only a new work/status-demo-10/ folder in this academy copy. If it exists,
stop and ask me to choose a fresh name. Create one small Python script for
the status-normalization demonstration above, including the three examples.
Explain the exact command, run it if Python is available, and show the actual
exit status and printed results. Do not modify academy source or assignments.
Do not install dependencies or commit anything.
```

The assistant should tell you the file it created and how to run it again. The directory `work/` holds private practice and is excluded from the distributed academy. A generated script that has not run is still useful to read, but its output remains unverified.

## What you should see

You should be able to connect each line of code to a requirement: trim the ends, change letter case, and return the new text. The three results should match the table. Ask why internal spaces remain and why blank text becomes an empty string. Those questions expose understanding more clearly than the number of files produced.

For the optional execution route, check that the result names the actual file and command, not merely “all done.” If only three examples ran, the claim is “these three examples matched,” not “the feature handles all input.” No learner completion should be recorded automatically.

## If it goes wrong

If the assistant adds a status whitelist or user interface, restate the one behavior requested. If Python is missing, return to the chat explanation or use the setup guide; installing an entire toolchain is not required to read this topic. If a generated program fails, provide the exact command and error rather than asking for an unrelated rewrite. Never paste passwords or private production logs into the demonstration.
