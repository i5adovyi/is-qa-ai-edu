# 02 · Ask for useful work without expecting mind reading

## Start here

You can already ask a question in ordinary language. This topic makes that request easier to check. It builds on [observations versus suggestions](01.md), but you do not need to finish an exercise first. We will use a tiny requirement and ask an assistant for testing ideas. No code or formal specification is required.

## The idea in plain language

A **prompt** is the request and information you give the model. A **task contract**, in this course, is simply an explicit agreement about the work: what you want, which information applies, what a useful result looks like, and what to do when information is missing. It is not a legal document or a special file format.

Suppose you tell a colleague, “Test the upload feature.” They would need to know the supported file types, size limits, expected errors, and whether you want ideas or working automated tests. An assistant lacks that background too. More confident wording does not replace missing requirements.

Four short labels usually help: **Task**, **Facts**, **Result**, and **Unknowns**. The task states the action. Facts contain the actual requirement or evidence. Result names the format you want. Unknowns tells the assistant how to handle gaps. This structure makes omissions visible to you as well as to the assistant.

An **acceptance criterion** is an observable condition that makes a result acceptable. “Be comprehensive” is hard to judge. “Each proposed test states an input and expected behavior supported by the supplied rule” is checkable. That does not mean every prompt needs a template. A simple request to explain one unfamiliar word can stay one sentence. Add structure when ambiguity could produce the wrong work.

Instructions guide the response; they do not enforce every boundary. A request saying “do not modify production” is useful communication, but actual account access and tool permissions determine what an application can do. For now, we will ask for discussion only and provide synthetic data.

## A small example

Here is a complete, deliberately narrow requirement:

```text
Rule R-7: a display name may contain 1 to 20 characters, inclusive.
Leading and trailing spaces are removed before the length check.
Nothing is specified about allowed symbols.
```

The request “Give me tests” might produce a large generic list, including invented rules about punctuation. A clearer request asks for three examples, each with an input, expected result, and rule reference; it also asks the assistant to separate unspecified behavior.

For instance, `" Ava "` becomes `"Ava"` before checking length, so it is within the stated range. Whether an emoji is permitted cannot be answered from R-7 alone. Even the meaning of “character” may need clarification before implementing Unicode-sensitive tests. Finding that gap is useful testing work, not a failed answer.

## Try it with Codex or Claude Code

1. Open either assistant's conversation using the [quickstart](../../docs/ASSISTANT-QUICKSTART.md) if needed.
2. Paste the prompt below. You can do this without opening the academy repository.
3. Compare each suggested expected result with R-7. Ask about one unclear result before asking for more cases.

```text
Task: help me understand test design for this synthetic requirement.
Facts: R-7 says a display name has 1 to 20 characters inclusive.
Trim leading and trailing spaces before checking length. No rule about
allowed symbols or Unicode counting has been supplied.
Result: give three worked test examples in a small table with input,
expected behavior, and the supporting part of R-7. Explain why each is useful.
Unknowns: list unspecified behavior separately. Do not invent a product rule.
This is explanation only. Do not create files or implement tests.
```

Then, if you want to see how instructions affect an answer, add: “Explain what would have been ambiguous if I had only said ‘test display names.’” You are studying the request itself. You are not asking the assistant to complete the original lesson's assignment for you.

## What you should see

The response should preserve the order of operations: remove outside spaces, then check length. It should separate unsupported assumptions from supplied rules. A table is useful here because you can inspect one row at a time; generating a separate document is unnecessary.

The key check is whether another person could tell what each proposed test is asserting. If an expected result depends on a guessed rule, label that dependence before relying on the test. Continue to [comparing prompt changes](03.md) when that distinction makes sense.

## If it goes wrong

If the assistant says emojis are forbidden, reply: “Show the supplied rule that forbids them; otherwise move this to unspecified behavior.” If it returns code, ask for one plain-language row first. If it asks fifteen questions before helping, narrow the task: “Use only the length and trimming rules; mention unresolved items without blocking this explanation.”

Sometimes the request really cannot be answered without a missing rule. “Unknown” with a useful question is then better than a fabricated expected result. Do not reward an assistant merely for always producing a definitive answer.
