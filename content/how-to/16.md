# 16 · Choose examples that reveal whether AI helps

## Start here

One impressive answer cannot tell you whether an AI assistant will handle tomorrow's work. An evaluation uses a chosen set of cases to examine behavior consistently. As an SDET, you already know that input selection matters; this topic extends that skill to variable language outputs. No statistics package, API key, or dataset-authoring assignment is required to begin. Allow about 20 minutes.

If evaluation itself is unfamiliar, read the [testing AI primer](../guide/04-evaluating-ai.md). Use the [assistant quickstart](../../docs/ASSISTANT-QUICKSTART.md) to enter the self-contained example below. You may understand a case in chat before creating any file.

## The idea in plain language

A **dataset** is a collection of examples. An evaluation **case** contains an input, the evidence the system may use, and criteria for an acceptable result. A **label** records the expected behavior. **Provenance** records where the case and label came from. An **evaluation rubric** is the rule used to judge the output.

For a calculator, one exact number may be the expected answer. For an AI explanation, several phrasings can be acceptable. You can still require important facts, forbid invented claims, and check whether the answer addresses the question. Avoid treating your preferred wording as the only correct wording unless exact formatting is part of the requirement.

A **development set** is used while improving the prompt or system. A **held-out set** is reserved for a later comparison, so you do not repeatedly tune to those same answers. If a held-out answer leaks into instructions or examples, it is no longer evidence of performance on unseen material. Renaming a familiar case does not make it independent.

For an SDET, useful cases include ordinary inputs, boundaries, missing evidence, contradictions, and failures with high impact. A synthetic course set teaches mechanisms but does not reproduce your employer's traffic distribution. Do not infer production reliability from twelve convenient examples. For a one-off low-risk draft, direct human review may be sufficient; repeated or consequential workflows need more systematic evidence.

## A small example

Consider a synthetic release-note assistant. It receives only:

```text
Change C1: The search box now accepts accented characters.
Test T1: Search for “café” returned the expected record in staging.
Deployment status: not supplied.
```

An acceptable summary can mention the search improvement and the staging observation. It must not claim the change is deployed to production or that all languages work. Two outputs can use different sentences and both be acceptable if they respect those boundaries.

The label is therefore not a single polished paragraph. It is a small rule: include the supported improvement, preserve the limited test scope, and avoid an unsupported production claim. Provenance could say “synthetic teaching case, checked against C1 and T1.” That explains why the label exists without suggesting it was observed in a real release.

## Try it with Codex or Claude Code

Paste the three-line fixture above with this request:

```text
Teach me how to evaluate a release-note assistant using only this synthetic
fixture. Do not access a repository, browse, or create a dataset file.
First explain input, allowed evidence, and expected behavior. Then show two
different acceptable one-sentence summaries and explain why neither may claim
a production deployment. Finally explain one important kind of case this
single example does not cover. Do not open academy answer keys or holdout data.
```

This is a worked teaching example, so you can see its explanation directly. For a chosen exercise, tell the assistant to withhold the answer until your attempt. The distinction keeps normal learning accessible without spoiling practice.

If you later open the academy repository, ask the assistant to show how its existing training cases and evaluation rules are stored, using only the training split. Ask it to explain one field at a time and to avoid modifying fixtures or opening held-out answers. The [evaluation-versus-demo article](../articles/evaluation-vs-demo.md) explains what the reference evaluation measures. A deterministic fixture run is not evidence of actual model performance.

## What you should see

The explanation separates the evidence from the criteria used to judge an answer. It should accept different supported wording, reject unsupported deployment claims, and admit that one case has limited coverage. Ask where each expected fact came from. An answer that sounds plausible but cannot be traced to the fixture should not become a trusted label automatically.

For a larger set, keep case IDs and split membership stable while comparing changes. Separate failures by category: a formatting error and an unauthorized action should not disappear inside one average. If policy is unclear, preserve the disagreement and clarify the policy rather than manufacture a definitive label.

## If it goes wrong

If the assistant produces dozens of near-identical examples, ask which new behavior each one tests. If it labels its own preferred answer correct without a rule, return to the requirement and evidence. If the model under evaluation sees the answer key, record that contamination and stop calling those cases unseen. If you cannot run a live model, case design and rubric review remain useful; mark live performance as unmeasured.
