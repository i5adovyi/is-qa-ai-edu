# 13 · Understand what controls an agent's next step

## Start here

You are not expected to know what a state machine is, draw one, or build an agent before this explanation. Start with something familiar: a test run has a status such as queued, running, passed, or failed. This topic explains how software decides which status can follow another, then connects that idea to an AI assistant. Allow about 20 minutes.

The [assistant quickstart](../../docs/ASSISTANT-QUICKSTART.md) shows where to paste the prompt below. A read-only conversation is enough. [Tool boundaries](../how-to/07.md) help explain why a proposed action needs checking, but you can ask for definitions here without completing earlier exercises.

## The idea in plain language

A **state** describes where a process is now. A **transition** is an allowed move to another state. A **state machine** is just a set of states and rules for those moves. For example, a test run should not become “passed” before its checks finish. You already reason about such rules when testing an order or account lifecycle.

A **loop** repeats work until a stopping condition is reached. A **deterministic** rule gives the same result when its relevant inputs and starting state are the same. These words describe ordinary software; neither requires an AI model.

An agent adds a model that can propose the next action. The **harness** is the surrounding software that supplies context, checks proposals, runs permitted tools, records results, and decides whether to continue or stop. The model might suggest reading a test report. The harness must still check that the requested report is allowed and exists. The model saying “finished” is not itself proof that the work succeeded.

For an SDET, this separation gives you testable boundaries: invalid requests, missing evidence, repeated actions, cancellation, and false completion. If your task has three predictable steps, a fixed workflow can be easier to understand and test than an autonomous planner. You do not need to add a model just to choose the next obvious step.

## A small example

Imagine a toy filename checker with three rules:

| Current state | Event | Next state |
| --- | --- | --- |
| `waiting` | start checking | `checking` |
| `checking` | filename ends in `.csv` | `accepted` |
| `checking` | any other ending | `rejected` |

Here is a complete demonstration, not an assignment to implement:

```python
filename = "report.csv"
state = "waiting"
print(state)
state = "checking"
print(state)
if filename.endswith(".csv"):
    state = "accepted"
else:
    state = "rejected"
print(state)
```

The variable `state` holds the current label. The `if` chooses between two paths using one observable condition. The program prints `waiting`, `checking`, then `accepted`. It is a fixed sequence with a decision, not a model-driven agent loop. The deliberately narrow rule checks a case-sensitive filename ending, not file content or upload safety.

## What you should see

You should be able to say what the current state means, what evidence permits the next move, and which states stop the process. For an agent, distinguish “the model proposed a tool call” from “the runtime executed it successfully.” A malformed proposal should not become a real tool call merely because the model asked confidently.

The small script is not a complete agent, durable state store, or reusable state-machine library. Its purpose is to make the underlying idea visible. You can continue reading once that idea makes sense; independent implementation is a later practice choice.

## If it goes wrong

If the explanation starts with graphs, enums, or orchestration, ask the assistant to return to three labels and one rule. If the program prints an unexpected state, check the filename and exact condition. If a demo is described as using an AI model, require the actual model-call evidence; ordinary Python execution does not establish model use. If an assistant reaches for a network connection, restate that this demonstration is local and self-contained.
