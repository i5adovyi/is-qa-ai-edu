# 14 · Resume interrupted work without doing it twice

## Start here

Imagine clicking “save,” seeing a timeout, and clicking again. Did the first save fail, or did only its response disappear? This is the central problem of recovery. You can understand it without knowing databases. Read [states and agent control](../how-to/13.md) first if workflow status is unfamiliar. Allow 20 minutes for the explanation; a local crash demonstration is optional.

Use the [assistant quickstart](../../docs/ASSISTANT-QUICKSTART.md) for tool setup. The first prompt uses invented facts in chat and needs no clone or credentials. This guide concerns software recovery; it does not ask you to test a real payment, email, or customer account.

## The idea in plain language

A **checkpoint** saves enough progress for a program to continue later. **Durable** means the record survives the process stopping. A checkpoint might say which operation was pending, which input version it used, and which result was already confirmed. A chat summary alone is not proof that a real action completed.

**Idempotency** means repeating the same logical operation has the same intended effect as doing it once. Setting a label to “reviewed” can have that property; adding a new comment every time usually does not. Systems often use an **operation ID**, a stable label for one intended action, so a retry can be recognized.

**Reconciliation** means checking durable evidence to resolve an uncertain outcome. The key idea is that “I did not receive success” and “nothing happened” are different statements. A server may commit the change, then lose the connection before the response reaches the caller.

For an SDET, recovery testing explores these awkward moments between an effect and its acknowledgment. You inspect what actually exists after interruption, rather than assuming the screen's error message describes the destination perfectly. A short read-only calculation may not need durable checkpoints; a long workflow or an action with lasting effects often does.

## A small example

A synthetic test-report service receives operation `attach-report-42` with report contents `summary-A`. It stores attachment `A17` and remembers that the operation produced it. The response is lost.

On retry, the caller sends the same operation ID and the same contents. The service can return `A17` instead of creating another attachment. If the caller reuses `attach-report-42` with different contents, the service should report a conflict according to its contract rather than quietly pretending it is the same request.

This requires real storage behavior. Merely adding an ID to a prompt does not make a remote service support deduplication. A new random ID on every retry also loses the connection between attempts. And retention matters: if the service forgets operation records after a time limit, its retry guarantee changes after that limit.

Paste this into either assistant's conversation box:

For an actual offline observation, open a local academy copy. Ask the assistant to explain and run the following first command with a fresh output directory:

```sh
python3 -m lab.cli demo --scenario crash-after-write --out work/recovery-demo-14
```

Its exit code **3** is intentional: the simulation stops after saving a draft. Have the assistant show you the relevant fields in `work/recovery-demo-14/store.json` and `checkpoint.json` without editing either file. Then, when you choose to continue, run:

```sh
python3 -m lab.cli resume work/recovery-demo-14/checkpoint.json
```

Ask which persisted record explains the resumed behavior and how many logical drafts exist before and after. These commands execute the supplied reference implementation, not a live AI model or your unfinished student helper. They are an observation route, not proof that you can implement recovery independently.

## What you should see

The interrupted reference run has a saved draft even though the workflow did not record ordinary completion. Resumption should reuse the recorded result and leave one logical draft and one durable write. You should be able to explain why another tool attempt can occur without another effect. The bundled store is a single-process teaching model, not a claim of exactly-once execution across arbitrary services.

If the demonstration's output differs, preserve the files and report the actual result. Never edit a checkpoint to manufacture a reassuring outcome or rerun into an occupied output directory without understanding what it contains.

## If it goes wrong

If the command cannot import `lab`, confirm the terminal is at the academy root. If Python is unavailable, use the chat route. If you cannot query a real destination and it has no documented safe retry mechanism, uncertainty remains: ask for human reconciliation instead of claiming definite failure or automatically repeating a consequential action. In the lab, inspect evidence before any repair.
