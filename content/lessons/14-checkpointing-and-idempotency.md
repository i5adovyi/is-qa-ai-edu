# 14 · Recover from crashes without duplicating work

Stage 5 · 90 minutes · Practitioner

Design checkpoints and idempotent operations so interruption becomes a recoverable state rather than a mystery.

## What you will be able to do

- Identify crash windows around writes and checkpoints.
- Use operation IDs to reconcile uncertain outcomes.
- Distinguish retryable failures from unresolved side effects.

## The idea

Reliable execution must account for interruption at inconvenient moments. A process can stop after a draft is saved but before success is recorded. On restart, the harness may believe the action never happened and save it again. The problem is not solved by telling the model to remember more carefully. It is a consistency problem between durable artifacts and durable state.

A checkpoint captures enough state to resume: task identity, completed operation IDs, evidence versions, current step and pending action. Store it in a format you can inspect. Validate it before resumption and reject impossible states. A checkpoint claiming completion without a referenced artifact should trigger reconciliation, not a cheerful final message.

Idempotency means that repeating the same logical operation has the same intended effect as performing it once. A stable operation ID lets the executor recognize a repeat and return the previous result. It must also detect an ID reused with different arguments. Otherwise, a caller can accidentally suppress a genuinely new action or overwrite an earlier one under the same identity.

Exactly-once effects across systems are difficult; do not promise them merely because your loop has retries. For the local Signal Desk sandbox, a transactional ledger can coordinate draft records and operation IDs. For a remote service, you need its documented idempotency or reconciliation behavior. A timeout after a write is an unknown outcome until you inspect the destination or safely retry using a supported key.

## Worked example

Consider operation `SD-114:draft:v1`:

```text
A. Record intent and arguments hash.
B. Save draft D-114 and operation result durably.
C. Record workflow step complete.
D. Return success to caller.
```

Crash after B but before C. On resume, look up the operation ID. If its stored argument hash matches, reuse D-114 and advance the workflow. If the hash differs, stop with a conflict. If no record exists, execution may proceed. In a database-backed implementation, use transactions for records that must change together; a handwritten ordering alone does not make writes atomic.

## Exercise 1 · Guided crash matrix

List crashes before A, between each pair of steps and after D. For every point, describe what durable evidence exists and what resumption should do. Identify which outcomes are known, unknown or conflicting.

**Deliverable:** five-row crash matrix: before A, A–B, B–C, C–D, and after D. **Pass:** the after-B case reuses the existing draft; no row equates a missing response with a failed write. An interruption *inside* B is an additional case: explain which transaction or atomic-replacement guarantee covers it rather than assuming two separate writes are atomic.

## Exercise 2 · Build recovery

Implement a local operation ledger using JSON plus careful atomic replacement, or SQLite if you know it. Save a draft under a stable operation ID, interrupt before workflow completion, and resume. Alternatively, inspect a checkpoint generated by the bundled lab and run `python3 -m lab.cli resume <checkpoint.json>` using the actual generated path.

For the bundled route, follow [Lab 05's crash-and-resume commands](../labs/05-idempotency-and-recovery.md#observe) in a new run directory. The crash command intentionally exits `3`; it is the pause point for inspection, not a setup failure. Preserve the store and checkpoint before resuming, then compare the draft and durable-write counts afterward. A normal completed demo is not the interrupted-write evidence this exercise requires.

**Deliverable:** checkpoint, operation record and before/after artifact counts. **Pass:** the interrupted run yields one logical draft; the resumed run records how it reconciled state; corrupted checkpoints fail clearly.

## Exercise 3 · Adversarial identity reuse

Reuse the operation ID with a changed draft body. Then remove the referenced draft while retaining the successful ledger entry. Finally, simulate a write timeout with no way to query the destination. Specify what the harness should do in each case, including when human review is necessary.

**Deliverable:** conflict and uncertainty traces. **Pass:** changed arguments are rejected; missing artifacts are detected; an unknowable remote result is not reported as definitely failed or definitely successful.

## Hints and solution outline

The key belongs to the logical action, not the retry attempt. A new random ID on every retry defeats deduplication. Store a normalized argument hash and result identifier with the key. In a local transaction, write the draft record and operation record together. On resume, verify that the artifact still exists and its content matches expectations. Never silently repair a conflict by overwriting evidence; preserve enough information for diagnosis.

## Reflection

Which part of your recovery relies on the filesystem or database guarantee? What changes when the action is a remote email send? How would you explain an unresolved outcome to an operator without encouraging a duplicate action?
